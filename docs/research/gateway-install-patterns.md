# Install and update patterns of comparable Pi-hosted daemons

> Research note, 2026-09-02. Question: how do self-hosted daemons that people
> run on a Raspberry Pi (Home Assistant / maker ecosystem) install, update,
> roll back and report their version, and what does that imply for the
> first `blaueis-gateway` release, where the options on the table are
> (A) git clone pinned to the latest release tag, (B) `pip install` from
> PyPI with unit + CLI shipped in the wheel, (C) `pip install` from a git tag
> URL. This note surfaces evidence; it does not make the decision.
>
> Every claim is cited to a primary source (official docs, the project's own
> install/update script, or its source tree). Script behaviour is described
> in prose, not copied.

## Summary

- Sixteen projects surveyed. Five mechanisms recur: (1) git clone tracking a branch; (2) git clone reset to the latest tag; (3) release tarball/zip fetched via the GitHub API; (4) language registry (PyPI / npm); (5) OS package repo (apt) with a bundled runtime.
- Among **Python** daemons the registry path (PyPI) is the dominant "stable" install (OctoPrint via OctoPi, ESPHome, Home Assistant Core, motionEye, Moonraker's package, OVOS); git clone is reserved for the "bleeding edge" path (Moonraker source, Klipper, wyoming-satellite) and Mycodo uses tag tarballs. **Node** daemons split three ways: npm global (Node-RED), git clone of `master` (zigbee2mqtt), apt with bundled Node (Homebridge).
- No surveyed wheel or npm package installs a systemd unit by itself. Every registry-based daemon pairs with an installer script (OctoPi build, `motioneye_init`, `install-moonraker.sh`, Node-RED script, OVOS/Ansible) or leaves the unit to the user (ESPHome, HA Core).
- "Update follows the latest tag/release" is the norm for anything with a stable channel (Pi-hole, Mycodo, Moonraker `stable`, OctoPrint `github_release`, registries by construction); "follow a branch" survives only where the branch *is* the release (zigbee2mqtt `master`) or for dev channels.
- Rollback is rarely a first-class feature: Moonraker tracks `rollback_version`; KIAUH does `git reset --hard HEAD~N`; Mycodo/Spoolman keep the previous directory; registry installs rely on pinning an older version; Pi-hole and zigbee2mqtt offer none.
- Version reporting mirrors the mechanism: `git describe` for clones (Pi-hole, Klipper, KIAUH, blaueis today), package metadata for registry installs (Moonraker's `python` type reads dist metadata and `direct_url.json`), compile-time or package version for binaries (evcc, Homebridge).
- Installer scripts are fetched from a fixed branch URL almost everywhere (Pi-hole `master`, OVOS `main`, Mycodo gh-pages, blaueis `main`); Node-RED is the one project that moved its script to a GitHub release asset (v2.0.0, 2024-06).
- Two maintainer-stated rationales matter for a single-maintainer project: Home Assistant deprecated its venv "Core" method in 2025 for support-burden reasons (2.5 % of installs, disproportionate issues), and Moonraker positions its PyPI package as "fewer updates, more stable" versus a git clone that "may receive frequent bleeding edge updates".

## Per-project notes

### Pi-hole

- Official one-liner is `curl -sSL https://install.pi-hole.net | bash`; the docs acknowledge that "Piping to bash is a controversial topic" and offer `git clone --depth 1` + running the script, or `wget` then run, as alternatives ([basic-install docs](https://docs.pi-hole.net/main/basic-install/)).
- `install.pi-hole.net` answers 302 to the raw `master` copy of `automated install/basic-install.sh` (observed redirect; target [raw script](https://raw.githubusercontent.com/pi-hole/pi-hole/master/automated%20install/basic-install.sh)).
- The installer shallow-clones the core and web repos (depth 20), checks out `master` and then hard-resets to the most recent tag (`git describe --abbrev=0 --tags`); the in-script comment explains this guards against commits added after tagging such as metadata or README tweaks. On update or repair the same function pulls and resets to the latest tag again. The FTL binary is not built from git: for `master` the installer asks the GitHub API for the latest release and downloads from `github.com/pi-hole/ftl/releases/download/…`; for other branches it uses `ftl.pi-hole.net/<branch>/`, with SHA1 verification. The systemd unit is a template under `advanced/Templates/` installed by the installer ([basic-install.sh](https://raw.githubusercontent.com/pi-hole/pi-hole/master/automated%20install/basic-install.sh)).
- `pihole -up` "Check Pi-hole Core, Web Interface and FTL repositories to determine what upgrades (if any) are required. It will then automatically update and reinstall if necessary" ([pihole command docs](https://docs.pi-hole.net/main/pihole-command/)); the docs insist on reading release notes first ([update docs](https://docs.pi-hole.net/main/update/)). Internally the update script fetches, compares local vs remote `git describe` tags on `master` (commit hashes on other branches), stashes local modifications, and re-runs the installer with repair/unattended flags; there is no rollback ([update.sh](https://raw.githubusercontent.com/pi-hole/pi-hole/master/advanced/Scripts/update.sh)).
- `pihole checkout` switches subsystems between `master`, `dev` or a named branch; it only lists branches, never tags or releases, and shows a warning that the feature is not supported unless a Pi-hole developer asks ([piholeCheckout.sh](https://raw.githubusercontent.com/pi-hole/pi-hole/master/advanced/Scripts/piholeCheckout.sh)).
- `pihole -v` reads `/etc/pihole/versions`, which a checker script fills with local versions from `git describe --tags --always`, branch from `git rev-parse --abbrev-ref HEAD`, short hashes, `pihole-FTL version`, and remote versions from the GitHub `releases/latest` API for `master` ([updatecheck.sh](https://raw.githubusercontent.com/pi-hole/pi-hole/master/advanced/Scripts/updatecheck.sh)).

### zigbee2mqtt (bare-metal path)

- Docs: install Node via the NodeSource script, `git clone --depth 1 https://github.com/Koenkk/zigbee2mqtt.git /opt/zigbee2mqtt`, `pnpm install --frozen-lockfile`, build; the systemd unit is typed by the user into `/etc/systemd/system/zigbee2mqtt.service`; "To update Zigbee2MQTT to the latest version" run `./update.sh` ([Linux install docs](https://www.zigbee2mqtt.io/guide/installation/01_linux.html)).
- `update.sh` fetches and counts upstream commits, stops the service, resets `package.json`/lockfile edits, `git pull`s (no rebase), reinstalls frozen deps, rebuilds, restarts; no backup or rollback ([update.sh](https://raw.githubusercontent.com/Koenkk/zigbee2mqtt/master/update.sh)).
- `master` is the release branch: the dev-branch page says to "Change 'dev' to 'master' to switch back to the release version" and warns the dev branch "could be less stable than the release version"; switching is `git fetch origin dev:dev`, `git checkout dev`, `git pull`, reinstall. No instructions for checking out a tag ([switch to dev branch](https://www.zigbee2mqtt.io/advanced/more/switch-to-dev-branch.html)).
- Version is exposed as `version` plus `commit` on the `zigbee2mqtt/bridge/info` topic ([MQTT topics](https://www.zigbee2mqtt.io/guide/usage/mqtt_topics_and_messages.html)); the FAQ notes that "Updating or downgrading Zigbee2MQTT to a different version" does not require re-pairing ([FAQ](https://www.zigbee2mqtt.io/guide/faq/)). Releases are published on GitHub and npm ([README badges](https://raw.githubusercontent.com/Koenkk/zigbee2mqtt/master/README.md)).

### OctoPrint (+ Software Update plugin)

- Download page lists OctoPi (image), pip (`python -m venv OctoPrint`, `OctoPrint/bin/pip install OctoPrint`, `octoprint serve`), Docker, `octoprint_deploy`, and a Windows installer; no service instructions on that page ([download](https://octoprint.org/download/)). OctoPrint 1.11.8 is on PyPI with `pip install OctoPrint` ([PyPI](https://pypi.org/project/OctoPrint/)).
- OctoPi (the dominant Pi path) builds a venv at `/opt/octopi/oprint` (symlinked to `/home/pi/oprint`) and runs `pip install $OCTOPI_OCTOPRINT_PACKAGE`, whose default is the PyPI name `OctoPrint`; no git clone is retained; the image enables `octoprint.service` ([build script](https://raw.githubusercontent.com/guysoft/OctoPi/devel/src/modules/octopi/start_chroot_script), [config](https://raw.githubusercontent.com/guysoft/OctoPi/devel/src/modules/octopi/config)). The shipped unit runs `/opt/octopi/oprint/bin/octoprint serve` as uid 1000, `WantedBy=multi-user.target` ([octoprint.service](https://raw.githubusercontent.com/guysoft/OctoPi/devel/src/modules/octopi/filesystem/root/etc/systemd/system/octoprint.service)).
- Software Update plugin: version checks `github_release`, `github_commit`, `git_commit`, `bitbucket_commit`, `pypi_release`, `httpheader`, `jsondata`, `command_line`; update methods `pip` ("Update by pip install-ing the supplied URL"), `update_script`, `single_file_plugin`, `python_updater`; no rollback is documented ([plugin docs](https://docs.octoprint.org/en/master/bundledplugins/softwareupdate.html)).
- OctoPrint's own entry uses a `github_release` check and a pip target shaped like `https://github.com/OctoPrint/OctoPrint/archive/{target_version}.zip` (the GitHub archive of the release tag, not PyPI); channels are stable (`master`), `rc/maintenance`, `rc/devel`; it requires an `octoprint` restart; current version comes from the `VERSION` constant; when tracking a prerelease the plugin enables exact-version pinning so it can move back to stable — not a general rollback ([plugin source](https://raw.githubusercontent.com/OctoPrint/OctoPrint/master/src/octoprint/plugins/softwareupdate/__init__.py)). No maintainer statement explaining GitHub-archive-over-PyPI was found.
- Version derivation is a custom versioneer/miniver-style module: a static version file written at distribution build, else git keywords, else `git describe --tags --abbrev=0 --always` plus commit distance; branch rules produce `{tag}.dev{distance}+g{short}`; `get_data()` returns version, branch, revision ([_version.py](https://raw.githubusercontent.com/OctoPrint/OctoPrint/master/src/octoprint/_version.py), [`__init__.py`](https://raw.githubusercontent.com/OctoPrint/OctoPrint/master/src/octoprint/__init__.py)).
- `octoprint_deploy` is `git clone`d and run with sudo; "You do not need to install OctoPrint using any Wiki instructions"; it "uses systemd services" per instance ([README](https://github.com/paukstelis/octoprint_deploy)). The official community setup guide for Raspberry Pi OS is behind an anti-bot wall and could not be read.

### Klipper + Moonraker (update_manager)

- Klipper docs point to KIAUH ("KIAUH can be used to install Klipper and its associated programs on a variety of Linux-based systems that run a form of Debian") and to MainsailOS images; no git clone or update command is given ([Installation](https://www.klipper3d.org/Installation.html), [Installation.md](https://raw.githubusercontent.com/Klipper3d/klipper/master/docs/Installation.md)).
- Klipper's own scripts: `install-octopi.sh` creates `~/klippy-env` and an init.d service (`/etc/init.d/klipper`, `/etc/default/klipper`) ([install-octopi.sh](https://raw.githubusercontent.com/Klipper3d/klipper/master/scripts/install-octopi.sh)); `install-debian.sh` writes `/etc/systemd/system/klipper.service` directly and enables/starts it; neither references a branch or tag ([install-debian.sh](https://raw.githubusercontent.com/Klipper3d/klipper/master/scripts/install-debian.sh)).
- Version: `git describe --always --tags --long --dirty`, falling back to a `.version` file, else `?` ([klippy/util.py](https://raw.githubusercontent.com/Klipper3d/klipper/master/klippy/util.py)).
- KIAUH: obtained by `git clone https://github.com/dw-0/kiauh.git`; installs Klipper, Moonraker, Mainsail, Fluidd, KlipperScreen ([README](https://github.com/dw-0/kiauh)). Klipper repo constant is `https://github.com/Klipper3d/klipper.git`, venv `klippy-env`, service and env templates in assets ([constants](https://raw.githubusercontent.com/dw-0/kiauh/master/kiauh/components/klipper/__init__.py)); units are rendered from a template as `klipper-<suffix>.service` ([klipper.py](https://raw.githubusercontent.com/dw-0/kiauh/master/kiauh/components/klipper/klipper.py)); the install and venv dirs are backed up before an update ([klipper_utils.py](https://raw.githubusercontent.com/dw-0/kiauh/master/kiauh/components/klipper/klipper_utils.py)). Git helpers: blobless clone (`--filter=blob:none`) with optional branch, update by `git pull`, rollback by `git reset --hard HEAD~N` (user picks N) with service stop/start, local/remote identity via `git describe HEAD --always --tags`, tags via the GitHub API ([git_utils.py](https://raw.githubusercontent.com/dw-0/kiauh/master/kiauh/utils/git_utils.py)). Changelog: v3.0.0 (2021-01-31) "All components get installed as systemd services. Installation via init.d was dropped completely!"; v4.0.0 (2022-05-29) rollback reworked to a commit count; v6.0.0 (2025-10-10) alternative repos manageable in-app ([changelog](https://raw.githubusercontent.com/dw-0/kiauh/master/docs/changelog.md)).
- Moonraker install docs offer two paths: the Python package ("The Python Package version of Moonraker will receive fewer updates, and should generally be more stable", for users who "do not need to run unofficial 3rd party extensions") via `wget` of `install-moonraker.sh` from raw `master`; or source ("This method of installation will clone Moonraker's git repository, and may receive frequent bleeding edge updates", for users "who … do not mind SSHing into the host to correct issues") ([installation](https://raw.githubusercontent.com/Arksine/moonraker/master/docs/installation.md)). The script decides by checking whether it sits inside a source tree; otherwise it `pip install`s the PyPI package into `~/moonraker-env`, then writes the unit with a heredoc plus an env file; `-f` forces regeneration ([install-moonraker.sh](https://raw.githubusercontent.com/Arksine/moonraker/master/scripts/install-moonraker.sh)). PyPI: `moonraker` 0.11.0, 2026-08-25 ([PyPI JSON](https://pypi.org/pypi/moonraker/json)).
- `update_manager` types: `web`, `git_repo`, `zip`, `executable`, `python`. Channel: "dev: Updates to the latest commit pushed to the repo"; `beta`/`stable` follow tags and "At least one tag is necessary for Moonraker to identify the software version … The tag must be in semantic version format, vX.Y.Z"; `pinned_commit` freezes; `managed_services`, `is_system_service`, `primary_branch`, `virtualenv`/`requirements`; Klipper and Moonraker are auto-configured; default refresh 672 h. `zip` type: "Software using the zip type should host their distribution in a zip file as a GitHub release. The zip file MUST contain release_info.json" ([configuration](https://moonraker.readthedocs.io/en/latest/configuration/), [configuration.md](https://raw.githubusercontent.com/Arksine/moonraker/master/docs/configuration.md)).
- `python` type implementation: reads the installed distribution metadata for the version; detects source as PyPI or GitHub by inspecting `direct_url.json` (VCS URL + commit); discovers updates with a pip dry-run report (PyPI) or the GitHub API (latest commit for `dev`, latest release for `stable`/`beta`); updates by `pip install` with a version pin or a git URL at a tag/commit; keeps `rollback_version`/`rollback_ref` and rolls back by re-running the update against them ([python_deploy.py](https://raw.githubusercontent.com/Arksine/moonraker/master/moonraker/components/update_manager/python_deploy.py)).
- API: status reports `version`, `remote_version`, `current_hash`, `remote_hash`, `is_dirty`, `detached`, `channel`, and `rollback_version` ("The version prior to the last update. This version is used during a rollback request"); endpoints `refresh`, `recover` (soft reset or re-clone), `rollback` ([update manager API](https://moonraker.readthedocs.io/en/latest/external_api/update_manager/)). Changelog: 0.9.0 (2024-07-25) added zip updates, pip-managed python apps and rollbacks; 0.9.2 (2024-07-30) added installing Moonraker's python package via pip ([changelog](https://moonraker.readthedocs.io/en/latest/changelog/)).
- Spoolman shows the coupling risk of the `zip` type: after the project changed its installer layout (uv), a user's `[update_manager Spoolman]` block failed with "Invalid path for option `requirements`" and unparsed `repo`/`persistent_files`/`managed_services` options ([Spoolman #830](https://github.com/Donkie/Spoolman/issues/830)).

### Node-RED (Pi install script)

- Docs: `bash <(curl -sL https://github.com/node-red/linux-installers/releases/latest/download/install-update-nodered-deb)`; it installs Node.js (ensures at least v20, installs v22 LTS if none), npm and Node-RED, will "setup Node-RED to run as a service", and "can also be used to upgrade an existing install"; armv6 support ends with Node 24 ([Raspberry Pi docs](https://nodered.org/docs/getting-started/raspberrypi)).
- The script installs with `npm i -g node-red@latest` unless `--nodered-version="X.Y.Z"` is given; other flags include `--node20/22/24`, `--restart`, `--confirm-install`, `--confirm-pi`, `--skip-pi`, `--allow-low-ports`, `--update-nodes`, `--nodered-user`. The unit is downloaded from the raw `master` `resources/nodered.service`, customised (memory, user, group, working dir) and only overwritten when the template changed; the script reloads systemd but starts the service only with `--restart`; on upgrade it removes the previous install, rebuilds native modules and migrates globally installed nodes; the installed version is read back with `npm ls node-red` ([script on master](https://raw.githubusercontent.com/node-red/linux-installers/master/deb/update-nodejs-and-nodered)).
- README recommends the `releases/latest/download` URL and says of the repository itself "Most users should never need this as the script above is the recommended way to install and upgrade" ([README](https://github.com/node-red/linux-installers)). Releases v2.0.0 (2024-06-09) onward carry the asset `install-update-nodered-deb`; v1.1.2 (2024-05-28) still used `update-nodejs-and-nodered-deb` ([releases](https://github.com/node-red/linux-installers/releases)). No written rationale for the move to release assets was found.

### Homebridge

- Recommended Raspberry Pi OS path: add the GPG key and `deb [signed-by=…] https://repo.homebridge.io stable main`, then `apt-get install homebridge`; the guide's purpose is to install Homebridge "as a service so it will automatically start on boot"; "You can update Homebridge and the bundled Node.js runtime by installing the latest version of the Homebridge package using apt" ([wiki](https://github.com/homebridge/homebridge/wiki/Install-Homebridge-on-Raspbian)).
- The deb "contains a self-contained Node.js installation and environment for Homebridge to run in" under `/opt/homebridge` (not on PATH), plus Config UI X and the systemd unit; config and plugins live in `/var/lib/homebridge` and "will not be affected by updates"; stated aim: "deploy Homebridge and the Homebridge UI in a secure and stable way, with no dependencies outside those available in the standard distribution repos", running "as a service user with no sudo / admin priviledges"; version via `apt list -a homebridge` ("apt versions do not start with a v") ([homebridge-apt-pkg README](https://github.com/homebridge/homebridge-apt-pkg), [raw README](https://raw.githubusercontent.com/homebridge/homebridge-apt-pkg/latest/README.md)).
- Package releases bundle fixed component versions, e.g. v2.0.18 stable (2026-09-01) = Node 24.20.0, UI 5.29.0, Homebridge 2.4.0, with separate beta/alpha/legacy tags ([releases](https://github.com/homebridge/homebridge-apt-pkg/releases)).

### ESPHome CLI

- Install: `pip install esphome`, preferably in a venv because "Many Linux distributions now refuse to pip install into the system Python and will fail with externally-managed-environment" ([installing](https://esphome.io/guides/installing_esphome)). PyPI 2026.8.2, 2026-08-31 ([PyPI](https://pypi.org/project/esphome/)).
- Update: `pip3 install -U esphome`; beta `pip3 install --pre -U esphome`; bleeding edge `pip3 install https://github.com/esphome/esphome/archive/dev.zip` with the caveat "the latest bleeding-edge version is not always stable" ([FAQ](https://esphome.io/guides/faq)).
- "The esphome version command shows the current ESPHome version and exits"; the built-in `dashboard` command was removed in favour of the Device Builder; no service unit is provided ([CLI](https://esphome.io/guides/cli)).

### Home Assistant Core (venv) — deprecated

- Announcement 2025-05-22: Core (Python environment) and Supervised are deprecated; notice from 2025.6, support ends with 2025.12. Rationale: "The Core and Supervised installation methods are not only complex for users to install and maintain — they're also challenging for the Home Assistant team to support"; they are 2.5 % of installations yet "generate more issues that are more difficult to solve" and place "a disproportionate burden on our community-driven support system"; new users "could sometimes be swayed into running Core or Supervised, and have a bad experience". After deprecation "issue reports will no longer be accepted" but "it will still be technically possible to update them" ([blog](https://www.home-assistant.io/blog/2025/05/22/deprecating-core-and-supervised-installation-methods-and-32-bit-systems/)). The docs were deleted on 2025-05-26 (commits `ce820fb` "Core: delete installation instructions" and `f4cb788` "Common tasks: remove core specific file") ([commit list 1](https://api.github.com/repos/home-assistant/home-assistant.io/commits?path=source/_includes/installation/core.md&per_page=2), [commit list 2](https://api.github.com/repos/home-assistant/home-assistant.io/commits?path=source/common-tasks/core.markdown&per_page=2)).
- Last published procedure: "This is an advanced installation process"; `useradd -rm homeassistant -G dialout,gpio,i2c`; venv at `/srv/homeassistant`; `pip3 install wheel` then `pip3 install homeassistant==<major>.<minor>.<patch>` where the pin is filled from site variables for the current release; first run `hass`; no systemd section ([core.md at last revision](https://raw.githubusercontent.com/home-assistant/home-assistant.io/5a4df61a676c53e60abbf435cb6bcb007dbd6be3/source/_includes/installation/core.md)).
- Last published update procedure: stop the service, `sudo -u homeassistant -H -s`, `source /srv/homeassistant/bin/activate`, `pip3 install --upgrade homeassistant` (unpinned), restart ([update.md](https://raw.githubusercontent.com/home-assistant/home-assistant.io/88b53742c77ecd3d4ae7ba5e39cb649ea58fc2c9/source/_includes/common-tasks/update.md)); specific version `pip3 install homeassistant==<version>` with downgrade guidance only for OS/Supervised ("do a partial restore of a backup instead") ([specific_version.md](https://raw.githubusercontent.com/home-assistant/home-assistant.io/88b53742c77ecd3d4ae7ba5e39cb649ea58fc2c9/source/_includes/common-tasks/specific_version.md)); beta `pip3 install --pre --upgrade homeassistant` ([beta_version.md](https://raw.githubusercontent.com/home-assistant/home-assistant.io/88b53742c77ecd3d4ae7ba5e39cb649ea58fc2c9/source/_includes/common-tasks/beta_version.md)); dev `pip3 install --upgrade git+https://github.com/home-assistant/core.git@dev` ([development_version.md](https://raw.githubusercontent.com/home-assistant/home-assistant.io/88b53742c77ecd3d4ae7ba5e39cb649ea58fc2c9/source/_includes/common-tasks/development_version.md)).

### Mycodo (Python, `curl | bash`)

- `curl -L https://kizniche.github.io/Mycodo/install | bash` installs to `/opt/Mycodo`; the version is shown at the top-left of the web UI; an "Upgrade System" upgrades "to the latest release … or restore to a previously-backed up version" ([README](https://github.com/kizniche/Mycodo)).
- The install script does not git clone: it queries the GitHub API for the latest release, downloads that tarball, extracts to `/opt/Mycodo`, runs `install/setup.sh`; it refuses to run as root and aborts if `/opt/Mycodo` exists ([install script](https://kizniche.github.io/Mycodo/install)). `setup.sh` enforces `/opt/Mycodo` and delegates venv creation and service installation to `upgrade_commands.sh` ([setup.sh](https://raw.githubusercontent.com/kizniche/Mycodo/master/install/setup.sh)), which enables `/opt/Mycodo/install/mycodo.service` from the tree ([upgrade_commands.sh](https://raw.githubusercontent.com/kizniche/Mycodo/master/mycodo/scripts/upgrade_commands.sh)).
- Upgrade: web UI or `sudo mycodo-commands upgrade-mycodo`; backups go to `/var/Mycodo-backups`; restore via the UI or `sudo mycodo-commands backup-restore <path>` ([upgrade docs](https://kizniche.github.io/Mycodo/Upgrade-Backup-Restore/)). The download step asks a helper for the latest tag within the same major (regex over the tags API) and fetches `github.com/kizniche/Mycodo/tarball/<tag>` into `/tmp/Mycodo-<version>`; a forced `master` upgrade uses the branch archive ([upgrade_download.sh](https://raw.githubusercontent.com/kizniche/Mycodo/master/mycodo/scripts/upgrade_download.sh), [github_release_info.py](https://raw.githubusercontent.com/kizniche/Mycodo/master/mycodo/utils/github_release_info.py)). The install step moves the current tree into `/var/Mycodo-backups/` then moves the new tree into place; on failure it records a status code but does not auto-restore ([upgrade_install.sh](https://raw.githubusercontent.com/kizniche/Mycodo/master/mycodo/scripts/upgrade_install.sh)). Backups are named `Mycodo-backup-<date>_<time>-<version>` (rsync excluding cameras, the venv and upgrade files) ([backup script](https://raw.githubusercontent.com/kizniche/Mycodo/master/mycodo/scripts/mycodo_backup_create.sh)). The current version is the `MYCODO_VERSION` constant in `mycodo/config.py`.

### blaueis-gateway today (baseline, from this repo)

- `scripts/install.sh` is fetched from raw `main`; it `git clone --depth 50`s the monorepo on `main` into `/opt/blaueis-gw`, creates a venv, `pip install -e`s `packages/blaueis-core` and `packages/blaueis-gateway`, copies the unit template with `User=` substituted, and symlinks the bash CLI (`scripts/install.sh`, `packages/blaueis-gateway/systemd/blaueis-gateway@.service`).
- `blaueis-gw update` fetches `origin main` (depth 50), compares `git describe --tags --always` of `HEAD` and `origin/main`, applies with `git pull --ff-only` + `pip install -e`, and `--rollback` is `git reset --hard HEAD~1` (`packages/blaueis-gateway/scripts/blaueis-update`).
- The daemon resolves `GW_VERSION` once at startup with `git describe --tags --always --dirty` in the install dir (fallback `unknown`), and the WebSocket `update` command runs `git pull --ff-only` + `pip install -e` and exits non-zero so systemd restarts it (`packages/blaueis-gateway/src/blaueis/gateway/server.py`).
- `packages/blaueis-gateway/pyproject.toml` declares a static `version = "0.1.0"` with plain setuptools, so package metadata and the git-describe string are already two different version sources.

## Patterns and rationale

**P1 — git clone tracking a branch, built in place.** zigbee2mqtt (`master` = release), Klipper/KIAUH, Moonraker source, wyoming-satellite, blaueis today. Version = `git describe`; update = `git pull`; rollback = `git reset --hard HEAD~N` (KIAUH) or Moonraker's stored `rollback_version`. Rationale voiced: Moonraker frames this as the path for people who "do not mind SSHing into the host to correct issues"; zigbee2mqtt keeps it workable by making `master` the release branch and isolating development on `dev`.

**P2 — git clone reset to the latest tag.** Pi-hole clones `master` but hard-resets to the newest tag so users never run post-tag commits, and its update check compares tags rather than commits; branch switching exists but is explicitly unsupported. Pi-hole also shows a hybrid: scripts from git, the compiled daemon from GitHub release assets.

**P3 — release archive of a tag, no git at runtime.** Mycodo (GitHub API → tag tarball → `/opt/Mycodo`, backup dir kept, restore from UI/CLI), Spoolman (release zip + `release_info.json`), Moonraker's `zip` type. Rollback falls out naturally (keep the previous directory); the cost is that the archive layout becomes an interface (Spoolman #830).

**P4 — language registry.** Python: OctoPrint/OctoPi, ESPHome, HA Core, motionEye, Moonraker package, OVOS; Node: Node-RED (`npm i -g`). Version = package metadata; update = `pip install -U` / `npm i -g @latest`; rollback = pin an older version; stable/beta/dev channels map onto `--pre` and git-URL installs (ESPHome, HA). Rationale voiced: Moonraker — "fewer updates, and should generally be more stable"; ESPHome — venv forced by `externally-managed-environment`. Counter-evidence: HA deprecated its venv path because it generated a disproportionate support load for 2.5 % of installs. Note that OctoPrint, although on PyPI, self-updates from the GitHub archive of the tag (the shape of option C).

**P5 — OS package repo with bundled runtime.** Homebridge (apt, bundled Node, unit in the deb, "no dependencies outside those available in the standard distribution repos", unprivileged service user), evcc (goreleaser deb via Cloudsmith, stable/unstable channels, `apt install evcc=<ver>` downgrade). Highest install/upgrade/rollback ergonomics, highest release-engineering cost; only seen with Go or a vendored Node runtime, not with Python.

**Dominance.** Python daemons: P4 dominates the "stable" path, P1 the "dev" path, with a script writing the unit in both cases; P3 appears where projects want atomic swaps and backups. Node daemons: no single pattern (P4 Node-RED, P1 zigbee2mqtt, P5 Homebridge). Across all: the installer script is fetched from a fixed branch URL except Node-RED (release asset), and units are never installed by the package manager of the language — always by an installer script, an image, a deb, or the user.

## Inputs for the A/B/C decision

Evidence-backed considerations, not a recommendation:

1. **Something still has to write the unit and the CLI.** No surveyed wheel installs a systemd unit; PyPI-based daemons pair with an installer (`install-moonraker.sh`, `motioneye_init`, OctoPi, OVOS) or leave it to the user (ESPHome, HA Core). Under B or C the installer script remains; the choice only changes what the script installs and whether git stays on the box.
2. **Where the installer script is served from is a separate axis.** Almost everyone serves it from a branch (Pi-hole `master`, OVOS `main`, Mycodo gh-pages, blaueis `main`); Node-RED serves it as a release asset while still pulling the unit template from `master`. A/B/C can each be combined with either.
3. **What "update" targets.** Branch-following (blaueis today, zigbee2mqtt, Klipper `dev`) versus tag/release-following (Pi-hole, Mycodo, Moonraker `stable`, OctoPrint, every registry). Tag-following avoids running post-tag commits (Pi-hole's stated reason) and matches the project's own policy that gateway and HA integration must move together on protocol bumps (`docs/versioning.md`). Under A this means the clone tracks tags, not `main`; under B/C it is implicit.
4. **Version source of truth.** A yields `git describe` (tag + distance + dirty), which is what Pi-hole, Klipper, KIAUH and blaueis report today; B/C yield package metadata, and Moonraker's `python` type shows that a git-URL pip install can still expose the source commit through `direct_url.json`. The repo currently has both (static `0.1.0` in `pyproject.toml` and git-describe at runtime); any option should collapse this to one.
5. **Rollback semantics.** `HEAD~1` (blaueis today, KIAUH `HEAD~N`) rolls back one *commit*, which equals one *release* only if the clone tracks tags. Registry/tag installs roll back by reinstalling the previous version, which requires remembering it (Moonraker stores `rollback_version`; Mycodo/Spoolman keep the previous directory). Pi-hole, zigbee2mqtt and HA Core document no rollback at all.
6. **Two packages, one release.** A installs `blaueis-core` and `blaueis-gateway` editable from one checkout, so they cannot drift. B needs both on PyPI with a pinned inter-dependency; C needs a `subdirectory` git URL per package at the same tag. Moonraker's `python` deployer handles both PyPI and GitHub-sourced packages and is a reference for the remote-update command, which today runs `git pull --ff-only` + `pip install -e`.
7. **Runtime dependencies on the Pi.** A keeps git (and the `safe.directory` handling already in `install.sh`) on the device; Mycodo, OctoPi and evcc run without git. C needs git only at install/update time; B not at all. ESPHome's note on `externally-managed-environment` means a venv is required under every option.
8. **Dev/bleeding-edge path.** Projects with a stable registry path keep a git route for developers (Moonraker's single script handles both; ESPHome `dev.zip`; HA `git+…@dev`). Choosing B or C for strangers does not preclude keeping A for the maintainer's own Pis.
9. **Support burden with a single maintainer.** HA's deprecation rationale (complex to install/maintain, disproportionate issue load) and Moonraker's "fewer updates, more stable" positioning both argue for offering strangers the path with the fewest moving parts; Spoolman #830 shows that whatever layout the updater depends on becomes a compatibility surface.
10. **Release-engineering cost.** P5 (apt) gives the best update/downgrade story but is only seen with Go binaries or a vendored Node runtime; P3 (tag tarball) needs no registry account but requires an install step that builds the venv; B needs PyPI publishing on every release; C needs only tags.
11. **Unit and path stability.** Every surveyed unit hard-codes the venv path (`/opt/octopi/oprint`, `~/moonraker-env`, `/srv/homeassistant`, `/opt/blaueis-gw/venv`); under B/C the installer still chooses that path, so the existing template-with-`sed` approach carries over unchanged.
